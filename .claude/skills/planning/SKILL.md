# /planning — 次に検証すべき仮説の抽出とテストカード立案

「重要度が高く・確信度が低く・未検証/検証中」の仮説（アサンプションマッピングの「重要×証拠なし」象限）を選び、検証計画を立てる。

> **共通規約**（プロジェクト解決・ID/接頭辞・リンク記法と `../` 深さ・.gitkeep・承認規律）は [CLAUDE.md「スキル共通規約」](../../../CLAUDE.md) が正典。以下は本スキル固有の手順。

## 手順

1. **状況を読む** — `wiki/stage.md`（現在ステージと移行基準の上書き）、`wiki/index.md`（全仮説）、対応する `playbooks/<stage>.md`（重点仮説タイプ・適した検証手法）を読む。あわせて **`wiki/views/board.md` の「現在地」節にある `- 次の一手（[[DEC-NNN]] より）: …` の行＝直近の意思決定が指した方向**を必ず読む（最新 DEC 本文の `## 次の一手` の射影。生成は `tools/gen_views.py` の `latest_dec_next_move`。ビューが古い/無ければ `python3 tools/gen_views.py board` で再生成する）。

2. **重要度を解決する** — 各仮説の `importance` が `auto` なら [ontology.md](../../../ontology.md) の「状態機械 > ステージ」表（正本 `ontology.yaml` の `stage-focus`）で解決（重点タイプ=8、それ以外=4）。手動指定（1-10）があればそれを優先。

3. **重要度×証拠の2軸マップを提示する** — 仮説を「重要度（高/低）× 確信度（低/高）」の4象限に配置して見せる。**優先すべきは「重要度高 × 確信度低 × 未検証/検証中」**。このとき **機械ランキング（重要度×確信度＝board の「次に検証すべき仮説」）と、手順1で読んだ DEC の「次の一手」を必ず並べて示す**。前者は現在の証拠状態の射影、後者は人が下した戦略判断であり、別の情報源である。

4. **検証手法を提案する** — 優先仮説に対し、playbook の「適した検証手法」から具体的な方法を提案する。ユーザーにどの仮説をどの方法で検証するか選んでもらう（`AskUserQuestion`）。
   - **機械ランキングと DEC の次の一手が食い違うときは、黙ってどちらかに従わない** — 「DEC が名指しした仮説群と、ランキング上位が一致しない」ことを明示的に言葉にしたうえで、(a) **DEC の次の一手を優先**（直近の戦略判断に従う）／(b) **ランキングを優先**（DEC 以降の状況変化を理由に。この場合は判断が古くなっているので `/deciding` で更新すべき旨を添える）をユーザーに選ばせる。**具体例として特定の仮説IDをここに書かない**（レコードが動くたびに例が腐る。実際の食い違いはその場の board から読む）。

5. **テストカード付き TEST 草稿を作る** — 選ばれた仮説ごとに `wiki/tests/` の既存最大+1で `TEST-NNN` を採番し、`templates/testcard.md`（テストカードのみのレコード）の `### 目的`／`### 方法`／`### 指標`／`### 成功基準` を記入して作成。**frontmatter の `riskiest-assumption` に「最もリスクの高い前提」（この実験で崩れたら全体が崩れる一点）を一文で必ず記入する**（board の背骨。成功基準と同じく検証前に確定し後から書き換えない）。frontmatter の `id` は**ファイル名と同じ接頭辞つき**にする（例 `id: SELF-TEST-001`）。**`data: real | simulated`**（この実験が実観測でおこなわれるのか、生成データなのか）も記入する — 架空判定（`fictional-cap`）の正本で、省くと本文の語からの推論に戻り、実データの実験が架空扱いになりうる。検証後の学びは別レコード **LEARN** として `/learning` が新規作成する（この TEST には学習カードを持たせない）。TEST は**学び LEARN が紐づくまでは自由に直してよく**、紐づいた後は成功基準と `riskiest-assumption` だけが凍る（不変ルール6）。本文に対象仮説 `[[H-NNN]]` を書く。ディレクトリに `.gitkeep` が残っていれば削除してよい。
   - **interview/demo 系はスクリプト草稿も併せて作る** — まず `AskUserQuestion` で**目的モード（反証型／発見型／ハイブリッド）を選ぶ**（心得の正典は `playbooks/interviewing.md`）。**TESTの `type` とステージに応じて基にする雛形を選び**、対象仮説を差し込んだ現場用スクリプト草稿を `wiki/tests/<PREFIX>-TEST-NNN-script.md` として作成し、TEST本文から相対mdリンクで参照する（`スクリプト: [<PREFIX>-TEST-NNN-script.md](<PREFIX>-TEST-NNN-script.md)`。付随物はビューに集計されないので、親から辿れないと到達不能になる）。

     **スクリプトは付随物（attachments.SCRIPT）なので frontmatter を必ず書く**（スキーマの正本は `ontology.yaml` の `attachments`・規約は [CLAUDE.md](../../../CLAUDE.md) の「スクリプト（付随物）」）。`id` はファイル名＝`<親TEST ID>-script`、`script-for` に親テストカード、`hypotheses` は**親の検証対象の部分集合**（発見型は仮説を伏せるので省略する）。

     下表は「TEST の `type` × ステージ → スクリプトの `type`」のルーティング（オントロジーに無いスキル固有の判断）。**基にする雛形のパスはここに書かない** — サブタイプ→雛形の対応は [ontology.md](../../../ontology.md) の「付随物」の『サブタイプと雛形』表が正本（`ontology.yaml` の `template` から生成。実在は `_selfcheck` が検証する）。

     | TEST `type` × ステージ | スクリプトの `type` | ねらい |
     |---|---|---|
     | `interview` × CPF/FPF | `problem-interview` | 課題の実在・自覚・実コスト（**ソリューションを見せない**） |
     | `interview` × PSF/SPF | `solution-interview` | 提示物への反応・乗り換え・〈支払い〉（ソリューションを**見せる**） |
     | `demo`（主に PSF） | `demo` | デモの司会・観察。詰まりどころとデモ後の行動を観る |

     - **反証型**: 対象仮説それぞれに**反証質問（何が観測されれば反証か）を必ず含め**、支持と反証を対で聞く。反証条件はテストカードの成功基準に事前登録する。
     - **発見型**: **すでに確証済みの前提・行動仮説・課題仮説にとらわれず**視野を広げる。既存仮説は相手に語らず伏せ、自発言及だけを listen-for として記録する。
     - 共通: The Mom Test の鉄則（過去の事実を聞く／ソリューションを見せない／誘導しない）と、対象者ごとの〈自認〉〈実コスト〉○×記録シートを含める（実例: `projects/ai-reskilling/wiki/tests/AIRE-TEST-003-script.md`＝反証型・`AIRE-TEST-002-script.md`＝発見型）。

6. **log を更新する** — `wiki/log.md` に追記:
   `## [YYYY-MM-DD] <type> | TEST-NNN テストカード作成（<対象H-NNN>） → 検証計画`
   （type は活動タイプ interview/demo/... のいずれか）

## 守ること

- **成功基準は検証開始前に確定する**。実施後（学び LEARN 紐付け後）は書き換えない（後知恵バイアス防止）。凍結されるのは成功基準と `riskiest-assumption` だけで、目的・方法・指標は実施の前後を問わず補正してよい。見出し名「成功基準」は機械が凍結範囲を特定する目印なので変えない。
- 一度に検証しすぎない。最重要の1-2本に絞るよう促す。
- **直近の意思決定を無視して計画しない**。最新 DEC の「次の一手」に触れずに機械ランキングだけで計画を立てると、人が下した判断が反復ループから落ちる（手順1・4）。
- この段階では確信度・ステータスを変更しない（それは `/learning` の仕事）。
- **確証バイアスに抗う**（`playbooks/interviewing.md`）。支持例だけを集める設計にしない。反証型なら反証質問を必ず含め、〈発言〉（好意・同意）だけで確信度の支持にしない。確証済みの前提・仮説にとらわれず視野を広げる発見型を選ぶ選択権を、ユーザーに毎回示す。
